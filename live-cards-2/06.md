# Карточка 6 — Resource limits

Перед выполнением карточки — в SSH на VPS:

```bash
cd /opt/cloud-practice/flask-todo-k8s
kubectl config use-context kind-cloud-lab2
kubectl config set-context --current --namespace=cloud-lab2
kubectl get pods
kubectl get deployments
```

Это справочник для чтения после выдачи карточки. Меню ничего не применяет.
Блоки с --help и explain — справка, остальные команды выполняй осмысленно и по очереди.
Для nano: Ctrl+O, Enter — сохранить; Ctrl+X — выйти.
Правки Deployment применяются через apply и создают новые Pod при изменении шаблона.
Во время карточки не применяй все исходные файлы без необходимости.


Задание: добавить или изменить requests и limits CPU/памяти.
В исходном Deployment раздел resources не задан. Изменения делаются при преподавателе.

```bash
kubectl explain deployment.spec.template.spec.containers.resources
kubectl describe nodes
```

resources задаётся у контейнера app, рядом с image, ports и env.
requests — ресурсы для расчёта размещения; limits — ограничение потребления.
CPU: 100m означает 0,1 CPU. Память: Mi и Gi — двоичные единицы.
Выбери значения с учётом VPS и числа реплик. requests не должны превышать соответствующие limits.

```bash
nano k8s/40-deployment.yaml
kubectl apply --dry-run=server -f k8s/40-deployment.yaml
kubectl apply -f k8s/40-deployment.yaml
kubectl rollout status deployment/flask-todo --timeout=180s
kubectl get pods
```

После этого выбери имя нового Pod и выполни kubectl describe pod с этим именем: покажи разделы Requests и Limits.
Не проверяй старый Pod, который уже завершается.
Pending после завышенных requests диагностируется через Events. OOMKilled указывает на завершение из-за нехватки доступной контейнеру памяти; CPU limit обычно вызывает throttling, а не OOM.
kubectl top требует Metrics Server; в нашем кластере он специально не устанавливался.
